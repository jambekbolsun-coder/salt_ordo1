# Salt Ordo: эксплуатация и действия владельца

Проверено 4 октября 2026 года. Основная база — Supabase `bgpcnfxwdndmrgkvcjez`, регион ap-south-1. Neon не используется. Реальные пароли, MFA-секреты и резервные копии в репозиторий не добавляются.

## Подключение Meta и Google

Vercel → проект Salt Ordo → Settings → Environment Variables → Production. После изменения переменных выполните Redeploy последнего успешного deployment. Значения не передавайте в чат и не добавляйте с префиксом `VITE_`.

| Переменная | Откуда получить / назначение |
|---|---|
| `SALT_GA4_MEASUREMENT_ID` | Google Analytics → Admin → Data streams → Web stream → Measurement ID |
| `SALT_META_PIXEL_ID` | Meta Events Manager → ваш Dataset/Pixel → Settings → ID |
| `SALT_META_ACCESS_TOKEN` | Meta Events Manager → Dataset → Settings → Conversions API → ручная настройка / Generate access token. Только сервер, минимально необходимый доступ |
| `SALT_META_API_VERSION` | Версия Graph API из актуальной настройки Meta, в формате `vNN.N`; выдуманного значения по умолчанию нет |
| `SALT_META_TEST_EVENT_CODE` | Необязательно: Events Manager → Test Events. Удалить после проверки |
| `SALT_MONITORING_WEBHOOK_URL` | Необязательно: приватный HTTPS-приёмник уведомлений владельца |
| `SALT_MONITORING_WEBHOOK_TOKEN` | Необязательно: Bearer-credential этого приёмника |

Публичные ID выдаются `/api/index?route=tracking-config`; токен Meta, ключ сессий и ключ шлюза никогда не возвращаются браузеру. При отсутствии ID соответствующий сервис не загружается. При отсутствии CAPI-токена или версии CAPI выключен; Pixel с настроенным ID может работать отдельно.

GA4 получает события только после аналитического согласия. Pixel/CAPI — после маркетингового. Начальные необязательные категории выключены. Версия согласия повышена до `2026-10-04.2`, поэтому посетителю с прежним выбором предлагается новый выбор. Отзыв останавливает новые события и удаляет доступные браузерные идентификаторы; уже отправленные события автоматически не удаляются. Начатую до отзыва сетевую передачу невозможно отозвать задним числом.

| Действие | GA4 | Meta |
|---|---|---|
| Страница | page_view | PageView |
| Каталог | view_item_list | ViewCatalog (custom) |
| Товар | view_item | ViewContent |
| Начало формы | form_start | FormStart (custom) |
| Заявка из контактной формы | generate_lead | Lead |
| Начало оформления | begin_checkout | InitiateCheckout |
| Успешное оформление заявки | request_complete | SubmitApplication |
| WhatsApp | whatsapp_click | Contact |
| Изменение согласия | cookie_consent_change | CookieConsentChange (custom) |

Изменение согласия отправляется только в категории, которые разрешены после изменения. При полном отказе событие никуда не отправляется. `Purchase` отсутствует: продажа учитывается сотрудником в CRM. ROI/ROAS не рассчитываются. Автоматическое отслеживание форм и Advanced Matching Meta не включены; в GA4 отключите Enhanced Measurement для форм и изменения history, чтобы сервис не создавал вторые события поверх событий приложения. Не включайте Meta Event Setup Tool с дублирующими событиями на этих же кнопках.

Pixel `eventID` совпадает с CAPI `event_id`; имя события одинаковое. Сервер хранит только ID, состояние доставки и счётчик попыток, без клиентских данных. Повторы ограничены, успешно доставленное событие повторно не отправляется. Это короткая повторная попытка, а не гарантированная долговременная очередь доставки. При длительном сбое Meta ошибка видна в безопасном журнале; CRM продолжает работать.

Перед включением на реальных посетителях проверьте в Meta Test Events и GA4 Realtime: отказ — нет запросов к провайдерам; аналитика без маркетинга — только Google; маркетинг без аналитики — только Meta; одинаковый ID Pixel/CAPI; заявка не порождает Purchase; отзыв останавливает события. Реальная доставка не проверена без ваших ID и токенов.

Атрибуция сохраняет UTM source/medium/campaign/content/term, fbclid, домен referrer, landing page без query, ID и названия кампании/группы/объявления. Она хранится в сессии браузера только при маркетинговом согласии и прикрепляется к новым обращениям, заказам и карточке клиента. В карточке отображается история полученных меток; фильтры ID/UTM работают по обращениям клиента. Диаграммы кампаний/объявлений показывают только реально полученные значения. Исторические записи без меток не дополнялись вымышленными значениями.

## Supabase Auth и MFA

На момент проверки тариф организации **Free**, подтверждённых TOTP-факторов у рабочих аккаунтов нет. Leaked Password Protection выключена и доступна на Pro и выше. Платный тариф не подключался. Самостоятельная регистрация пока разрешена в Supabase (`disable_signup=false`); в приложении страницы регистрации нет, а самостоятельно созданный пользователь не получает staff/CRM-доступ. Через подключённый MCP изменение Auth settings недоступно, CLI не авторизован — переключатели не считались выполненными.

Действия владельца:

1. [Authentication → Sign In / Providers](https://supabase.com/dashboard/project/bgpcnfxwdndmrgkvcjez/auth/providers): **Allow new users to sign up = OFF**, **Allow anonymous sign-ins = OFF**. Не выключать Email sign-in. Существующие пользователи продолжат входить, сотрудников создаёт владелец через админку.
2. [Authentication → Attack Protection](https://supabase.com/dashboard/project/bgpcnfxwdndmrgkvcjez/auth/protection): после осознанного перехода на подходящий тариф **Leaked Password Protection = ON**. Текущие пароли автоматически не заменяются. [Официальные ограничения](https://supabase.com/docs/guides/auth/password-security).
3. [Authentication → Multi-Factor](https://supabase.com/dashboard/project/bgpcnfxwdndmrgkvcjez/auth/mfa): проверить, что **TOTP enrollment/verification включены**. Не включать глобальное обязательное MFA до подключения владельца и остальных администраторов.
4. Открыть [Профиль → Двухэтапный вход и сессии](https://salt-ordo1.vercel.app/admin/security). Подтвердить текущий пароль, отсканировать QR своим приложением, ввести код. Секрет отображается только на экране подключения и не сохраняется в localStorage/логах. Проверить новый вход во втором браузере до выхода из первого.
5. Повторить для остальных администраторов. Записать ответственного за восстановление; защитить MFA также сам аккаунт Supabase и менеджер паролей.

Без подтверждённого фактора вход остаётся обычным. После подтверждения сервер требует AAL2 для CRM и административного proxy; SQL-проверки ролей также учитывают MFA при прямом обращении к Supabase. Страница `/admin/mfa` проверяет код и меняет идентификатор cookie сессии. «Доверенные» бессрочные устройства не создаются: каждая серверная сессия ограничена 8 часами, владелец видит только свои сессии и может завершить остальные. Отдельного списка чужих сессий нет.

Восстановление: сначала используйте резервное устройство/резервирование приложения-аутентификатора. Если это невозможно, уполномоченный владелец организации после проверки личности открывает Authentication → Users → нужный пользователь → MFA factors и удаляет утраченный фактор. Затем пользователь завершает остальные сессии и заново подключает MFA. Если потерян доступ самого владельца, нужен его доступ к Supabase Dashboard или доверенный участник организации. Это административный процесс; обхода MFA одним паролем нет. Приложение не выпускает recovery-коды. Не отправляйте QR/секрет/коды в поддержку или CRM.

Лимиты BFF: 10 запросов/сек одновременно по IP и пользователю; логин 5/мин по IP и 10/15 мин по хешу email; MFA 5/мин на пользователя; изменения CRM 30/мин; экспорт 3/мин; изменение пароля 3/15 мин. При превышении — 429 и Retry-After. Прямой Supabase Auth дополнительно защищается собственными [лимитами провайдера](https://supabase.com/docs/guides/auth/rate-limits); настройки Dashboard не выдаются за изменённые.

## Мониторинг

Публичный адрес: `https://salt-ordo1.vercel.app/api/index?route=health`. Ответ только `{"status":"ok"}` или `{"status":"unavailable"}` с HTTP 200/503; запрос проходит через серверный шлюз и проверяет доступность БД. Ошибки БД, схема, ключи и клиентские данные не выдаются. Health-check ограничен общим лимитом API; проверяйте раз в минуту, а не десять раз в секунду.

Vercel → проект → Logs: структурированные записи `request_failed`, route, status, request_id, timestamp. Нет ФИО, телефонов, URL query, SQL, тела запроса, user_id, IP, токенов или исходного объекта ошибки. Серверные сбои входа, записи, отчётов и доставки Meta видны здесь. Провайдерские логи Supabase/Vercel имеют собственные настройки доступа и хранения.

Для уведомлений подключите приватный HTTPS endpoint через две `SALT_MONITORING_*` переменные. Он получает тот же ограниченный JSON, опционально проверяет Bearer token и уведомляет владельца. Таймаут 2 секунды, одинаковые уведомления подавляются на минуту внутри одного процесса. Централизованную дедупликацию и проверку подписи/токена настройте на приёмнике. Внешний аккаунт/платная подписка/получатель не создавались. Настройте в своей системе отдельный монитор HTTP health-check с уведомлением после 2–3 последовательных сбоев и восстановлении. Не отправляйте сырые runtime-логи в публичный чат.

## GitHub и выпуск

`.github/workflows/checks.yml` запускается на push и pull_request в main. Node 24, npm ci из lock-файла, lint, тесты, SQL в PGlite, production build, сканирование истории/клиентского bundle, npm audit с отказом при high/critical. Права GitHub Actions только contents:read; реальные Supabase credentials и production-база не используются. Auth в HTTP-тестах — явно обозначенный симулятор, SQL и HTTP handler настоящие. Реальный TOTP владельца не подключался автоматически.

Рекомендуется Settings → Rules → Rulesets: требовать успешный `verify` перед merge в main. Сейчас Vercel автодеплой связан с GitHub и сам по себе не ждёт завершения Actions; обязательные проверки на PR предотвращают попадание непроверенного кода в main. Правила репозитория без запроса не ужесточались.

Репозиторий можно сделать приватным: уже опубликованный Vercel-сайт останется публичным. Перед переключением убедитесь, что Vercel GitHub App имеет доступ именно к этому репозиторию и ваш тариф Vercel поддерживает такой тип приватного репозитория/владельца. После изменения выполните тестовый push и проверьте новый deployment. Видимость не менялась. Сканер не нашёл секретов, но это не математическая гарантия отсутствия всех возможных секретов; приватность не заменяет их отзыв при утечке.

Новые миграции применяются адресно после изолированных тестов; не запускайте `db push` вслепую: исторические версии локальных миграций и старого production-журнала различаются. Добавлены поля и функции без удаления клиентских записей. При ошибке выпуска откатите приложение на проверенный deployment; новые колонки допустимо оставить. После подключения MFA не откатывайте на старый код без MFA: применяйте исправление вперёд, сохраняя проверку AAL2. SQL-откат не должен удалять таблицы и историю клиентов.

## Проверка на настоящем телефоне

Физическая установка на iPhone/Android и поведение экранной клавиатуры не подтверждались браузерной эмуляцией. Владельцу:

- iPhone Safari: открыть `/admin/login` → Поделиться → На экран «Домой». Android Chrome: меню → Установить приложение / Добавить на главный экран. Проверить имя и иконку Salt Ordo Admin, запуск внутри `/admin/`.
- Войти, при подключённом MFA подтвердить код; повернуть телефон, открыть меню, список, фильтры и карточку.
- Проверить поля с экранной клавиатурой: ввод телефона/суммы, прокрутку к Сохранить, отсутствие перекрытия кнопок, масштаб текста. Проверить диалог архива без подтверждения для реальных клиентов.
- Скачать CSV, открыть в Files/Downloads и Excel/Numbers, убедиться в кириллице и правильном разделении столбцов `;`.
- Отключить интернет: приложение должно показать нейтральную offline-страницу, а не список клиентов. Включить интернет, выйти, снова отключить интернет и нажать «назад»: закрытые данные не должны появляться.
- Отдельно на публичном сайте отклонить cookies, открыть каталог/товар; затем включить только аналитику, только маркетинг и отозвать через «Настройки cookies». WhatsApp проверять своим обычным способом — номер не менялся.

Для безопасной проверки создания/продажи/архива используйте `npm run dev:isolated`, а не рабочие клиентские записи. Тестовый сервер содержит только синтетические данные, запрещает внешние серверные запросы и не включён в production.
