# WhatsApp Coexistence — Salt Ordo

Интеграция расширяет существующую CRM, Supabase `bgpcnfxwdndmrgkvcjez` и BFF Vercel. Отдельной CRM нет. Рабочий номер берётся из существующих настроек сайта и никогда не изменяется интеграцией. Реальное подключение требует действий владельца в Meta; наличие кода не означает, что Meta одобрила приложение или конкретный номер.

## Проверенная архитектура

- React/Vite, маршруты React Router, общий раздел `src/pages/admin/Crm.jsx`.
- Существующие `salt_crm.clients`, `inquiries`, `sales`, `sources`, `audit` используются без переноса данных. WhatsApp не создаёт вторую запись в `public.leads`.
- `clients.phone` уникален, используется существующая нормализация и `record_inquiry`. Источник клиента остаётся первоначальным; новое сообщение имеет собственный источник в `inquiries`.
- Вход через существующий Supabase Auth и HttpOnly-сессию BFF. Подключение проверяет роль `owner` на сервере и в RPC; чтение CRM разрешено существующим `owner`/`admin`. MFA не меняется.
- Приватная схема закрыта для `anon`/`authenticated`. Единственный серверный RPC добавлен в существующий gateway с проверкой секретного заголовка. Секретов в Vite bundle нет.
- PWA не меняет manifest, worker, иконки и offline-страницу. CRM/API не попадают в offline-кэш. Meta SDK разрешён только политикой административной страницы.

## Официальный сценарий Meta

Проверены официальные страницы 5 октября 2026 года:

- [Coexistence: onboarding WhatsApp Business App users](https://developers.facebook.com/documentation/business-messaging/whatsapp/embedded-signup/onboarding-business-app-users)
- [Embedded Signup v4](https://developers.facebook.com/documentation/business-messaging/whatsapp/embedded-signup/version-4)
- [Tech Provider onboarding](https://developers.facebook.com/documentation/business-messaging/whatsapp/embedded-signup/onboarding-customers-as-a-tech-provider)

Используется новая конфигурация Embedded Signup v4. В SDK: `response_type: code`, `override_default_response_type: true`, `extras.featureType: whatsapp_business_app_onboarding`, `sessionInfoVersion: "3"`. Номер принимается только после события `FINISH_WHATSAPP_BUSINESS_APP_ONBOARDING`. WABA проверяется сервером, Phone ID получается из списка номеров этого WABA. Сервер сверяет номер с настройками магазина, `is_on_biz_app === true` и `platform_type === CLOUD_API`. Обычные `/register`, `/deregister`, перенос, удаление аккаунта и изменение PIN не вызываются.

После подписки WABA обязательны запросы `smb_app_data`: сначала `smb_app_state_sync`, затем `history`, в течение 24 часов после подключения. Успешные request ID сохраняются и не запрашиваются повторно. При неопределённом сетевом исходе повтор останавливается с `SYNC_UNCERTAIN`: нужно проверить получение webhook/состояние запроса у Meta, а не слепо повторять одноразовую операцию. При отказе от истории новые сообщения продолжают работать. Импортированная история и исходящие echoes не создают новые обращения и не завышают отчёты.

## Переменные Vercel

Project **salt-ordo1 → Settings → Environment Variables → Production**. Значения никогда не помещать в Git, чат или frontend:

| Переменная | Назначение |
|---|---|
| `META_APP_ID` | ID настоящего Meta App; отдаётся только вошедшему владельцу для SDK |
| `META_WHATSAPP_CONFIG_ID` | ID новой конфигурации Facebook Login for Business / Embedded Signup v4 с Coexistence |
| `META_APP_SECRET` | Секрет приложения; серверный обмен кода и проверка подписи webhook |
| `WHATSAPP_WEBHOOK_VERIFY_TOKEN` | Независимая случайная строка для проверки callback в Meta |
| `WHATSAPP_TOKEN_ENCRYPTION_KEY` | Отдельные случайные 32 байта в base64; AES-256-GCM для динамического токена |
| `WHATSAPP_GRAPH_API_VERSION` | Поддерживаемая версия Graph API, выбранная в настоящем Meta App, в формате `vNN.N` |

Существующие `SALT_SUPABASE_URL`, `SALT_SUPABASE_PUBLISHABLE_KEY`, `SALT_GATEWAY_SECRET`, `SALT_SESSION_KEY`, `SALT_APP_ORIGIN` остаются. Префикс `NEXT_PUBLIC_` здесь не используется: проект Vite, а ID передаются через защищённый endpoint. Реальный access token получается автоматически, вручную вводить его в браузер нельзя. В базе хранится только AES-GCM ciphertext, отдельные nonce/tag и версия; AAD связывает шифротекст с WABA и номером.

Ключ шифрования и Verify Token генерируйте криптографическим генератором и сохраняйте напрямую в защищённые переменные Vercel/менеджер секретов. После добавления переменных сделайте **Redeploy**. Не заменяйте ключ шифрования работающего подключения без контролируемого перешифрования либо повторного подключения. Резервная копия базы без отдельно защищённой копии ключа не позволяет восстановить токен.

## Что настроить в Meta вручную

1. Использовать реальный Business portfolio и Meta App, которому доступен официальный Coexistence. Пройти требуемую Meta проверку бизнеса/Tech Provider и App Review. Для Embedded Signup нужны одобренные `whatsapp_business_management` и `whatsapp_business_messaging`; дополнительные Marketing API permissions не запрашиваются автоматически.
2. В **Facebook Login for Business → Configurations** создать конфигурацию **Embedded Signup v4**, выбрать WhatsApp Cloud API product и вариант подключения существующего WhatsApp Business App / Coexistence. Не использовать обычное добавление номера. В настройках приложения разрешить домен `salt-ordo1.vercel.app` и HTTPS origin `https://salt-ordo1.vercel.app` для JavaScript SDK. Следовать требованиям конкретной конфигурации Meta к OAuth domains.
3. В **WhatsApp → Configuration → Webhooks** (или **Webhooks → WhatsApp Business Account**, в зависимости от интерфейса Meta) задать callback:

   **https://salt-ordo1.vercel.app/api/whatsapp/webhook**

   Verify Token — значение **`WHATSAPP_WEBHOOK_VERIFY_TOKEN`** из Vercel. Не путать с App Secret или access token.
4. Подписать поля **`messages`, `account_update`, `history`, `smb_app_state_sync`, `smb_message_echoes`**. Contacts, statuses, errors поступают внутри соответствующих payload, отдельного поля `contacts` для выбора здесь нет. Подписка приложения на выбранный WABA выполняется сервером после signup.
5. Убедиться, что приложение разрешено для реальных пользователей, а номер/регион/аккаунт поддерживают Coexistence. Нельзя обходить отсутствие поддержки переносом номера.

## Как владельцу подключить действующий номер

1. Обновить WhatsApp Business на основном телефоне. Сделать предусмотренную WhatsApp резервную копию переписки; проверить доступ к Business portfolio и номеру. Не удалять WhatsApp Business и аккаунт.
2. Войти как владелец Salt Ordo, открыть **Клиенты → Настройки CRM → WhatsApp Business**.
3. Нажать **«Подключить WhatsApp»**, разрешить окно Meta, войти в свой Meta-аккаунт.
4. Выбрать **существующий WhatsApp Business App номер**, совпадающий с рабочим номером в настройках Salt Ordo. Подтвердить привязку в приложении на телефоне по официальным шагам Meta. Если предлагается удалить аккаунт/номер из приложения или мигрировать его — отменить.
5. Дождаться подписки webhook и запуска синхронизации, оставить приложение на телефоне открытым. Проверить настоящий номер, дату, сотрудника и состояние соединения в CRM.
6. Написать на рабочий номер с другого телефона: клиент должен появиться один раз; следующее сообщение — в той же карточке. Ответить из WhatsApp Business на телефоне и проверить echo (если Meta передаёт его для данного устройства).
7. Проверить обычное сообщение, переход с сайта с сохранённым кодом и реальную CTWA-рекламу. Не отправлять фиктивную рекламу в production. Если человек удалил код из текста, источник сайта достоверно восстановить нельзя — используется WhatsApp без рекламы.

Основное приложение продолжает работать в официальном Coexistence, но Meta может отключить/потребовать переподключить связанные устройства и изменить доступность disappearing/view-once/live-location/broadcast функций. Регулярно открывайте основное приложение (Meta указывает ограничение длительной неактивности). Совместимость и доступность конкретного номера определяет Meta; код Salt Ordo не гарантирует одобрение.

## API и данные

- `GET /api/index?route=whatsapp`: безопасное состояние; ID/config только владельцу.
- `POST /api/index?route=whatsapp`: `prepare`, `exchange`, `complete`, `check`, `retry`; owner-only, CSRF/origin, session-bound state 10 минут, 5 операций в минуту. Код сразу передаётся серверу POST, не хранится в браузере. Токены Graph идут в Authorization header; App Secret/code — в теле обмена, не URL.
- `GET /api/index?route=whatsapp&view=messages&id=<client UUID>&offset=0`: 50 сообщений на страницу; доступ только существующим администраторам.
- `POST /api/index?route=whatsapp-click`: функциональный код перехода, страница/товар/категория; 10 переходов в минуту на IP. Без marketing consent не сохраняются UTM/fbclid/referrer/session. Ссылка продолжает работать при ошибке API.
- `GET/POST /api/whatsapp/webhook`: Meta verification / raw-body HMAC-SHA256. Лимит 1 MiB и 10 запросов/секунду/IP, превышение `429` с `Retry-After`. `200` только после сохранения/обработки; при временной ошибке `503` для повторной доставки Meta.

Миграция **`20261005134208_whatsapp_coexistence.sql`** создаёт только новые интеграционные таблицы: `whatsapp_connection`, `whatsapp_signup`, `whatsapp_clicks`, `whatsapp_events`, `whatsapp_messages`, `whatsapp_statuses`, `whatsapp_contact_names`. Последняя — временный 7-дневный кэш имён при синхронизации, не вторая клиентская база. Успешно обработанный payload очищается; остаются идентификаторы и статус. Неудачные нормализованные события доступны только серверу и повторяются владельцем, до 20 попыток. Медиа сохраняются как метаданные, без скачивания файлов и без публичных URL проксирования.

Уникальные message ID и event key, блокировки по телефону и `FOR UPDATE SKIP LOCKED` защищают от дублей. Повтор после сбоя не создаёт второе обращение. Исторические сообщения неизвестных контактов хранятся без клиента до его первого нового обращения; затем связываются по нормализованному номеру. Чужие WABA/Phone ID игнорируются даже при корректной подписи. Неизвестные типы сохраняются без падения.

Каждое новое входящее сообщение считается отдельным обращением, а не отдельным клиентом. История/echo/status не считаются обращениями. Продажа может быть связана с выбранным обращением в существующей форме; без выбора сохраняется прежняя логика первого источника. Конверсия обращений считает обращения выбранного периода с привязанной неотменённой продажей; клиентская конверсия отдельно показывает долю WhatsApp-клиентов с продажей в периоде. ROI/ROAS не вычисляются.

## Поддержка и восстановление

- `TOKEN_REVOKED`: войти владельцем и подключить повторно. Пароли сотрудников не менять. `PARTNER_REMOVED`/`ACCOUNT_OFFBOARDED`: токен очищается, подписка помечается отключённой.
- `SYNC_UNCERTAIN`: проверить состояние запуска и входящие sync webhook в Meta; не сбрасывать `*_requested_at` без подтверждения Meta, что запрос не был принят. После подтверждения оператор может исправить только соответствующее sync-поле серверным доступом. Обычные новые сообщения при сохранённой подписке продолжают обрабатываться.
- `DB_*`: безопасный SQLSTATE без SQL/клиентских данных. Исправить причину и нажать «Повторить обработку». События, достигшие 20 попыток, требуют диагностики оператором, а не бесконечного автоматического повторения.
- Не удалять таблицы для отката. Совместимый rollback: вернуть предыдущий Vercel deployment, оставить новые таблицы и записи. Перед первым реальным подключением проверить резервное копирование Supabase согласно существующему `docs/BACKUP-RESTORE.md`. Миграция повторяемая; destructive down migration намеренно отсутствует.

## Изолированные проверки

`npm test` проверяет реальный HTTP handler, HMAC, challenge, роли/CSRF/state, шифрование, код→token→Graph subscription/sync с изолированным провайдером, дубли, SQL, CRM и PWA. `npm run typecheck` проверяет новые серверные JS-модули с TypeScript/JSDoc; весь прежний frontend не объявляется типизированным.

Для ручного теста: `npm run dev:isolated` запускает PGlite с 10 000 синтетических клиентов и запрещает внешние серверные запросы. Затем `npm run test:whatsapp:local` отправляет подписанный синтетический webhook только в `localhost:5173`. Это отдельный процесс разработки; production не имеет тестового обхода подписи. Учётная запись тестовой среды выводится локальным скриптом. Не запускайте нагрузочные/синтетические сценарии против основного домена.

## Телефон после настоящего подключения

- Android Chrome / iPhone Safari: войти, открыть настройки/список/карточку/отчёты; проверить 320–430 px, фильтры, прокрутку и кнопки.
- Запустить Embedded Signup в обычном браузере; если standalone PWA ограничивает popup/Meta login, открыть тот же защищённый раздел в браузере. Закончить setup и вернуться в установленное приложение.
- Проверить клавиатуру в формах, запись продажи по обращению, CSV, возврат к фильтрам.
- Проверить входящее сообщение, ответ с основного телефона и timestamps Бишкек UTC+6.
- Android: установить через меню Chrome. iPhone: «Поделиться → На экран Домой». Проверить открытие CRM в установленном PWA.
- Выйти, отключить сеть: клиентские записи не должны открываться из offline-кэша; допускается только нейтральная offline-страница.

Физический телефон и реальное подключение Meta нельзя считать проверенными по эмуляции браузера или mock Graph API. Эти шаги завершаются владельцем после предоставления настоящей конфигурации.
