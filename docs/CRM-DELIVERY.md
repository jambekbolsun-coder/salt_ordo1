# Salt Ordo: CRM, отчётность и защита данных

Проверено 4 октября 2026 года. Проект расширен на существующем React 18 / Vite / React Router, Supabase и Vercel. Переписывания магазина или переноса в Neon нет.

## Результат

Рабочий раздел: https://salt-ordo1.vercel.app/admin/clients

Проверенный production deployment с кодом приложения: https://salt-ordo1-4mb5l59ap-jambekbolsun-coders-projects.vercel.app

Коммит приложения: `9bfcec916112329b9b54b83cda028539c6582959`, ветка `main`. Последующий коммит содержит финальную миграцию прав, тесты и этот отчёт; код приложения тот же. Автодеплой GitHub → Vercel работает, deployment приложения имеет статус READY.

Добавлены обзор, база, карточка клиента, отчёты, источники и настройки CRM. В карточке — обращения, заметки, продажи, отмена продажи с причиной и журнал изменений. Номер нормализуется; повторный номер добавляет обращение к существующему клиенту. Конкурентное редактирование обнаруживается по версии записи. Архивирование обратимо и требует подтверждения.

Поиск и фильтры выполняются на сервере: имя/телефон, даты, источник, кампания, регион, сотрудник, результат, наличие продажи и архив. Сортировки: новые, старые, сумма, последняя активность обращения. Параметры находятся в URL и сохраняются при возвращении из карточки. Список загружается по 25 записей, история — блоками по 50. На телефоне используются карточки и раскрывающаяся панель фильтров.

Отчёт показывает клиентов, новые и повторные обращения, Meta Ads/сайт, продажи, сумму, средний чек, источники, регионы, товары и динамику по дням/неделям/месяцам. Выбранный период сравнивается с предыдущим равной длины. Время — Asia/Bishkek, валюта KGS. Продажи и обращения считаются по датам событий; фильтр источника клиента использует первый источник. Источник продажи фиксируется на момент записи. Архив по умолчанию исключён. Регионы и товары показывают первые 100 групп; дни без событий подразумевают ноль. Расходы рекламных кабинетов не подключены, поэтому ROI/ROAS не выдумываются.

Экспорт базы и отчёта — CSV UTF-8 с BOM, разделителем `;`, экранированием и защитой от формул. База выгружается серверными блоками по 100 без ограничения первой страницей. Файлы содержат персональные данные: владелец управляет их дальнейшим хранением.

## База Supabase

Использован существующий проект `bgpcnfxwdndmrgkvcjez`, PostgreSQL 17.6. Существующие таблицы и данные сохранены, одна прежняя заявка перенесена в CRM. Некорректные старые номера остаются в старом разделе и регистрируются для ручного разбора.

Закрытая схема `salt_crm` не доступна браузерным ролям; на таблицах включён RLS. Доступ через ограниченные RPC шлюза с серверной проверкой активного сотрудника.

| Таблица | Назначение |
|---|---|
| clients | Клиент, уникальный нормализованный телефон, WhatsApp, регион, интерес, первый источник, кампания, ответственный, результат, даты, архив и версия |
| inquiries | Отдельные обращения, рекламная атрибуция JSON, внешний провайдер/ID и дата события |
| sources | 9 заданных источников и их доступность |
| notes | Рабочие заметки с автором и временем |
| sales | Положительная сумма, источник/кампания, автор, идентификатор повторной отправки, отмена без удаления |
| audit | Изменения CRM, вход/выход, смена пароля, экспорт, настройки |
| settings | KGS, Бишкек, срок ручного пересмотра хранения |
| import_issues | Старые заявки с некорректными номерами |
| sessions | Хеш непрозрачной сессии и зашифрованные токены Supabase; срок 8 часов |
| rate_limits | Общие для всех экземпляров Vercel скользящие счётчики запросов |
| gateway_keys | Хеш отдельного отзываемого ключа шлюза |
| public_requests | Повторная отправка checkout возвращает прежний результат |

Сотрудники используют существующую `public.staff` и Supabase Auth. Добавлены индексы дат, источника, кампании, региона, ответственного, результатов, внешних ID, связей и trigram-поиска имени/телефона. В `public.leads` добавлены только поля CRM; insert-триггер синхронизирует новое обращение. Оформление заказа и создание заявки теперь выполняются одной транзакцией.

## Применённые миграции

Все семь выполнены в указанном Supabase, их версии сверены с журналом миграций:

1. `20261004083302_crm_workspace.sql` — схема, ограничения, индексы, перенос заявок, API, сессии и лимиты.
2. `20261004083305_crm_reports.sql` — расчёты отчётов и аутентификация шлюза.
3. `20261004083308_crm_public_intake.sql` — публичная форма и защита изменений сотрудников.
4. `20261004083808_crm_indexes.sql` — trigram и дополнительные индексы связей.
5. `20261004084244_crm_security_refinements.sql` — скользящий лимит, повторные операции, аудит, отмена продажи, закрытие bootstrap первого владельца.
6. `20261004085121_crm_atomic_checkout.sql` — атомарный и идемпотентный checkout.
7. `20261004090600_crm_public_api_cutover.sql` — закрытие прямых старых записывающих RPC для anon/authenticated после проверки нового production.

Откат: `supabase/rollback/crm_pause.sql` и `crm_resume.sql` сохраняют таблицы/записи, а не удаляют их. Сначала вернуть предыдущий Vercel deployment, затем выполнить pause от владельца БД. Resume восстанавливает схему и переносит пропущенные заявки; затем вернуть новый deployment и применить cutover прав. Цикл pause/resume и сохранность записей проверены автоматически в изолированном PostgreSQL PGlite. На production откат не выполнялся.

Исторические SQL-файлы прежнего проекта не все присутствовали в журнале Supabase до этой работы. Не следует запускать весь старый каталог миграций повторно поверх production; новые семь уже применены.

## Переменные окружения и функции

Настроены в Vercel Production, значения в отчёт/Git не включены:

- `SALT_SUPABASE_URL`
- `SALT_SUPABASE_PUBLISHABLE_KEY`
- `SALT_GATEWAY_SECRET`
- `SALT_SESSION_KEY`
- `SALT_APP_ORIGIN`

Существующие `VITE_SALT_SUPABASE_URL` и `VITE_SALT_SUPABASE_PUBLISHABLE_KEY` остались публичной конфигурацией. Главный `SUPABASE_SERVICE_ROLE_KEY` не переносился во frontend или Vercel: он остаётся в Supabase Edge environment. `crm-gateway` использует отдельный проверяемый ключ, ограниченный списком RPC. Отключение стандартной JWT-проверки этого шлюза компенсировано собственной обязательной аутентификацией до выполнения запроса. `create-staff` сохраняет JWT-проверку и проверяет владельца. Обе функции опубликованы.

Preview автоматически не получает доступ к production-секретам. Для отдельного стенда нужны отдельные Supabase/env и точный origin. Локальный запуск полного приложения: `npm run dev:full`, секреты — только в игнорируемом `.env.local` по образцу `.env.example`.

## Исправления безопасности

- CRM защищена на сервере и в БД, доступ только активным owner/admin. Manager/content запрещены. Источники, настройки и управление сотрудниками меняет владелец.
- JWT больше не сохраняются в браузерном storage. Сессия — непрозрачная HttpOnly/Secure/SameSite=Strict cookie с префиксом `__Host-`; токены зашифрованы AES-256-GCM в закрытой схеме.
- Выход отзывает серверную сессию, очищает интерфейс и сообщает другим вкладкам. При отсутствии сети локальная блокировка требует завершить выход до восстановления доступа.
- Мутации проверяют точный Origin и специальный заголовок. CRM-поля разрешены явно, даты/UUID/номера/суммы/размеры проверяются, SQL использует параметры и статические запросы. React экранирует текст.
- API: максимум 10 запросов в скользящую секунду по пользователю и IP, HTTP 429 и Retry-After. Вход: 5/мин по IP, 10/15 мин по хешу email; записи CRM: 30/мин; публичные формы: 5/мин; экспорт: 3/мин; пароль: 3/15 мин; сотрудники: 5/15 мин. Это лимиты API приложения, не всей инфраструктуры Supabase/CDN.
- Прямые публичные RPC записи закрыты, чтобы не обходить проверку согласия и лимиты.
- Исправлена возможность администратора управлять другим администратором через create-staff; bootstrap первого владельца закрыт. Существующие два аккаунта сохранены, пароли не менялись.
- Устранены дубли checkout при повторе запроса и ошибка шлюза при успешном пустом ответе аудита.
- Экспорт защищён от spreadsheet formula injection. Клиентские данные и токены не выводятся в публичные логи.
- Обновлена уязвимая транзитивная dev-зависимость brace-expansion; npm audit не обнаружил уязвимостей.

Supabase Advisor после cutover: публичных SECURITY DEFINER RPC для anon больше нет. Оставшиеся 8 предупреждений authenticated относятся к существующим функциям каталога и помощникам RLS с проверками ролей. 12 информационных сообщений RLS без policies — намеренный запрет браузерного доступа в закрытой схеме. Новые индексы пока отмечаются unused из-за небольшого объёма данных. Leaked Password Protection в Supabase Auth остаётся выключенной настройкой проекта; её включение описано ниже. Это не юридическая гарантия и не внешний пентест.

## Cookies и PWA

На первом посещении равнозначны «Принять всё», «Отклонить необязательные» и «Настроить». Необязательные категории выключены. Сохраняются версия и дата; срок выбора — 180 дней. В футере и политиках доступно изменение/отзыв. До согласия не создаются аналитические идентификаторы и не отправляются события; маркетинговая атрибуция сохраняется только при отдельном согласии. После отзыва новые события блокируются, браузерные идентификаторы очищаются. Уже полученные записи не удаляются автоматически. Новых Meta/Google ключей и пикселей не добавлялось.

Manifest, иконки, service worker, scope `/admin/`, установка и offline-страница сохранены. SW хранит только нейтральную страницу отсутствия сети, не клиентскую базу/API. Закрытые ответы имеют no-store. Новые маршруты находятся внутри PWA scope. Установка на физическом iPhone/Android и экранная клавиатура устройства недоступны в этой среде; проверены browser viewport, assets и автоматические сценарии SW, а не физическая установка.

Единственная тестовая карточка «Проверка CRM — тестовая запись» архивирована, её продажа отменена и не участвует в обычных отчётах. История теста сохранена. Транзакционные тесты production не оставили заказов. Масштабный нагрузочный тест не выполнялся; перед существенным ростом базы следует измерить отчёты/экспорт на ожидаемом объёме.

## Будущий WhatsApp webhook

Подготовлены отдельные обращения, нормализованный телефон, `external_provider` + `external_id` с UNIQUE, атомарное объединение и идемпотентная запись, даты событий, source/campaign, UTM, campaign/adset/ad ID и name, fbclid/referrer, аудит. Это позволяет добавить приём сообщений без дублирования клиента.

Сам webhook, подписки Meta, отправка сообщений и изменение рабочего номера не выполнялись. При будущем подключении потребуется отдельный серверный endpoint, проверка подписи Meta, безопасное хранение app secret/verify token, очередь повторной доставки и правила разрешённой обработки данных. Ключи не следует передавать в чат или включать в VITE-переменные.

## Действия владельца

1. Войти в `/admin/clients` существующим аккаунтом. При обновлении старой вкладки вход потребуется снова. Два ранее указанных аккаунта активны.
2. На телефоне открыть `/admin/` в Chrome/Safari и воспользоваться разделом «Приложение»/системным «На экран Домой». Проверить установку и клавиатуру именно на своём устройстве.
3. Выбрать ответственных, проверять полноту регионов/источников и записывать фактическую продажу отдельно от заявки. Архив доступен фильтром; тестовую карточку восстанавливать не нужно.
4. Проверить реквизиты оператора, основания и сроки хранения в политиках. Настройка срока — напоминание о ручном пересмотре, не автоматическое удаление.
5. В Supabase Auth включить Leaked Password Protection, если доступна на текущем тарифе. Для дальнейшего усиления доступа оценить MFA и ограничения самостоятельной регистрации. Не передавать пароли сотрудникам через публичные каналы.
6. Настроить подходящее резервное копирование/PITR под тариф и периодическую проверку восстановления. При росте данных проверить нагрузку, время отчётов и экспорт больших выборок.
7. Если понадобится WhatsApp Business API, подключать его отдельной задачей с проверкой подписи; текущая работа не требует действий с рабочим номером.
