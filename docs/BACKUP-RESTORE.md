# Резервное копирование и восстановление Salt Ordo

## Проверенный статус

Организация Supabase на тарифе **Free**. Доступные через Dashboard автоматические ежедневные копии гарантируются для платных тарифов; на Free нельзя считать, что у владельца есть готовая восстанавливаемая копия. Список фактических снимков через предоставленный коннектор недоступен, а CLI не авторизован. Автоматический backup, срок его хранения и успешное восстановление production **не подтверждены**. PITR — платная опция, в этой работе не включалась.

[Supabase Database Backups](https://supabase.com/docs/guides/platform/backups) указывает: Pro — 7 дней ежедневных копий, Team — 14, Enterprise — до 30; Free рекомендуется регулярно выгружать вне платформы. PITR требует подходящего платного тарифа и compute. Проект → **Database → Backups → Scheduled backups / Point in Time** показывает доступные копии и границы восстановления. Проверьте этот экран прежде, чем рассчитывать на копию. Платный переход выполняет только владелец.

Архивирование в CRM обратимо. При ошибочном SQL DELETE без подходящей резервной копии восстановление не гарантируется. Удаление всего Supabase-проекта также удаляет его платформенные копии. Резервная копия БД не содержит сами файлы Supabase Storage — фотографии нужно копировать отдельно.

## Безопасная процедура

1. Выделить зашифрованный каталог **вне Git-репозитория, папки Vercel и общедоступных синхронизируемых папок**, с доступом только владельцу/резервному администратору. Подойдёт зашифрованный том и отдельная зашифрованная off-site копия в приватном хранилище с MFA и версионированием. Ключ расшифрования хранить отдельно в менеджере паролей.
2. Использовать актуальные официальные Supabase CLI и Docker Desktop. Выполнить `supabase login` на доверенном компьютере, затем привязать отдельную служебную папку к проекту `bgpcnfxwdndmrgkvcjez`. Пароль БД вводить через защищённый prompt/секрет-хранилище; не помещать его в команды, GitHub Actions, shell history или чат. Не менять пароль только ради этой инструкции.
3. Из каталога резервных копий выполнить стандартный экспорт ролей, схемы и данных. Флаги проверены через CLI `--help`:

```sh
supabase db dump --linked --role-only -f roles.sql
supabase db dump --linked -f schema.sql
supabase db dump --linked --data-only --use-copy -f data.sql
supabase db dump --linked --schema supabase_migrations -f history_schema.sql
supabase db dump --linked --schema supabase_migrations --data-only --use-copy -f history_data.sql
```

4. Проверить завершение каждой команды без ошибки, ненулевые размеры и наличие `salt_crm` в схеме/данных. Отдельно убедиться, что копия охватывает auth-пользователей, MFA и необходимые customizations; стандартный dump управляемых схем и их изменений имеет особенности. Свериться с [актуальной инструкцией Supabase CLI backup/restore](https://supabase.com/docs/guides/platform/migrating-within-supabase/backup-restore), особенно разделами auth/storage и encryption root key. При Vault/column encryption логического dump недостаточно без сохранения соответствующего ключа.
5. Отдельно сохранить файлы Storage, конфигурацию Auth/URL/providers/SMTP, список Edge Functions и значения необходимых секретов в защищённом менеджере. Git хранит код и миграции, но не значения секретов. Не публиковать дампы даже в приватном Git-репозитории.
6. Создать зашифрованный архив, записать checksum, время, версию CLI, статус и размер без клиентских данных. Перенести копию off-site, проверить чтение и checksum. Открытые SQL-файлы не должны оставаться в Downloads/общей папке; удалять их только после проверки зашифрованной копии.

Режим: ежедневно, перед значимыми изменениями схемы и перед массовым импортом. Рабочая рекомендация хранения — 7 ежедневных и 4 недельных копии; владелец должен согласовать срок с политикой персональных данных. При таком расписании возможна потеря изменений после последней успешной копии (до суток). Для меньшего допустимого окна нужна более частая копия или PITR.

Эта инструкция не запускает автоматическое копирование. Надёжный автоматический запуск требует выбранного владельцем защищённого хранилища, секрет-хранилища и контролируемого планировщика вне публичного CI; их учётные данные не предоставлены. До настройки назначьте ответственного и проверяйте журнал копирования каждый день.

## Проверка восстановления

Раз в месяц и после изменения схемы восстановить копию в **отдельный закрытый тестовый проект**. Не менять production connection string и не направлять сайт на тестовый проект. Использовать инструкции Supabase для согласованных версий схемы, ролей и данных; `psql --single-transaction --variable ON_ERROR_STOP=1` прекращает восстановление при ошибке. Во время восстановления следовать официальному порядку отключения триггеров, чтобы не создать повторные обращения из leads.

Проверить количество записей, контрольные суммы/агрегаты, FK, CRM list/detail, фильтры, суммы отчётов, RLS, MFA, каталог и Storage. Не отправлять из копии реальные письма, уведомления, Meta-события или WhatsApp. Не восстанавливать старые активные пользовательские сессии как доверенные; в тестовом проекте закрыть восстановленные сессии и использовать отдельный тестовый staff-аккаунт. Записать фактическое время восстановления и найденные проблемы. Лишь успешная тренировка подтверждает пригодность копии; такая тренировка на production-данных в этой задаче не выполнялась.

## Если база повреждена

1. Остановить операции записи в приложении и интеграциях, сохранить безопасные технические сведения об инциденте. Не продолжать ручные массовые правки и не удалять проект.
2. Найти последнюю проверенную копию до инцидента; при наличии PITR выбрать момент до ошибочной операции. Оценить изменения, которые будут потеряны.
3. Сначала восстановить в закрытом отдельном проекте и проверить данные. Решить, можно ли точечно вернуть записи с сохранением свежих корректных изменений.
4. Только после проверки и согласованного окна простоя выполнять production restore/переключение. Dashboard restore временно делает проект недоступным. Проверить Auth, ключи шлюза, Edge Functions, Storage, RLS, CRM и основной домен после восстановления.
5. Завершить старые сессии, при компрометации отозвать затронутые ключи, проверить health-check и создать новую проверенную копию. Задокументировать фактическую потерю данных, не скрывая её.

В этой работе production не выгружался в файл, GitHub, Vercel или публичное хранилище; оплата backups/PITR не выполнялась.
